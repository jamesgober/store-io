# store-io v0.4.1 &mdash; Release fix

**A patch release for one defect, present since 0.3.0: a region release running at the same time as a provisioning on another thread could destroy the new region's data. Every 0.4.0 and 0.3.x user who releases regions while other threads provision should upgrade.** The on-disk format and the public API are unchanged: a 0.4.0 store opens with 0.4.1, and code that compiled against 0.4.0 compiles against 0.4.1.

```toml
[dependencies]
store-io = "0.4.1"
```

## What was wrong

- Releasing a region takes three steps: mark it released in the region table (the commit), write its header's Released state, and deallocate its data area.
- The release let go of the store's metadata lock after the first step. From then on, the table already named the extent free, and a provisioning on another thread could reuse it: a released extent of exactly the same length is reused for a new region.
- If a provisioning placed, filled and committed a new region there before the release finished, the release's two late writes landed in the new region:
  - the deallocation punched through its data area (Windows trims in place instead), including bytes the new region had already given durable receipts for;
  - the header write went over one of the new region's header slots, which could leave it unavailable at the next open.
- It needs a release and a provisioning of the same extent length on two threads, with the provisioning reaching placement in that window. A single-threaded program, or one that never releases while provisioning, was never affected.

## What 0.4.1 does

- **The release holds the metadata lock until its space is deallocated.** Provisioning already holds the same lock for its whole duration, so a provisioning now runs entirely before or entirely after a release, and never sees an extent the release is still writing to. No new lock order is introduced.

## How it was found and verified

- Found in the cold review of the v0.5 design, which asked what happens to space a release has freed while the release is still running.
- A unit test checks, deterministically, that the lock is held while the space is deallocated (a simulator hook observes the lock from the releasing thread); a second test provisions into just-released space, asserts the extent was reused, and reads the new region's durable bytes back after a reopen. A mutation entry that reintroduces the early unlock is caught by the tests.
- The full test suites, clippy, rustdoc, loom, the conformance suite on NTFS, ext4 and XFS, the kernel matrix, the crash replay, the fail-stop job and the mutation run all pass.
- **Performance gates.** GitHub moved its Linux runners to a kernel 7.0 image with a real `null_blk` device (whose writes are split into 124 KiB pieces) during this release. On it, every gate passes except two rows in code this fix does not touch: G6 (sequential 1 MiB writes: 77% of fio's best, against at least 90%) and G15 (8 durable writers at 1.34x one writer, against at least 1.5x, where a flush costs only ~14 µs; it passed in another run on the same image). On the previous image (kernel 6.17) both passed for 0.4.0. Both are being investigated for 0.5. G1 (a lone durable write) measured store-io 0.75 µs over the raw system call on the new image.

## Upgrading

Replace `0.4.0` with `0.4.1`. No code changes are needed.
