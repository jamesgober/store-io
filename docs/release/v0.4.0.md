# store-io v0.4.0 &mdash; io_uring and the engine layer

**io_uring on Linux, through store-io's own binding, and a `Submitter`: many reads and writes in flight from one thread with the same integrity rules as the blocking calls. The blocking calls are now built on that engine layer.** `0.x` releases make no compatibility promise; see Upgrading.

```toml
[dependencies]
store-io = "0.4.0"
```

## What is new

**The `Submitter`** (`Store::submitter`). One thread keeps many appends, page writes, reads and barriers in flight without blocking:
- Buffers come from the store's pool (`take_buf`), with no copy; completions (`reap`, `wait`) carry the caller's tag, the buffer, and the outcome.
- A write's ticket is minted only once every byte has transferred; a durable write's completion carries its receipt once the write is durable: after a flush covering it has succeeded, or at completion on a power-safe store (unless the region forces data sync). Flushes are shared with every other writer in the store.
- A write that fails after it was issued is `DurabilityUnknown` and poisons the store, as for a blocking call.
- `waker()` ends a `wait` from another thread. Dropping a submitter waits for everything in flight.

**io_uring on Linux** (`StoreOptions::linux_tier`: `Auto`, the default; `Uring`; `Sync`):
- store-io's own binding, no third-party crate. Every ring starts disabled, is restricted to reads, writes, NOP and cancel, then enabled.
- **Nothing ever runs on the kernel's worker threads.** Every read and write carries `RWF_NOWAIT`; what the kernel would block on is finished by one ordinary system call, and counted (`store_io::io_uring_fallbacks()`). CI checks that no io-wq worker ever appears.
- A submitter's ring belongs to its thread. Parallel blocking work (page batches, large reads, scans) uses shared rings. A blocking call's single operation runs inline with one system call, which is faster than a ring round trip for an operation the caller waits for at once.
- `Auto` uses io_uring where the kernel accepts both ring flavours (Linux 6.1 and later), else the synchronous tier; the choice and its reason are in `StoreReport::io`, and `Store::io_path()` keeps counting as queues are made.
- **A direct descriptor** (`StoreOptions::register_file`, on by default): a submitter's ring registers the container, so its reads skip the kernel's file lookup (reads 1.03x to 1.08x of an unregistered ring, measured in CI on a memory-backed device; writes take the unregistered path). Reads use a read-only twin of the container (a second open file description, which holds no lock); writes stay on the store's own, so a dead owner's write in flight keeps the store locked until it lands. Best effort.
- **No registered buffers, ever.** The CI kernel matrix found that a read into an io_uring registered buffer never completes on Linux 6.5.0 and 6.6.0 (and its process then cannot exit). No probe tells those kernels apart, so store-io never registers buffers, and its rings refuse the fixed-buffer opcodes (checked when the crate compiles).

**The blocking calls are built on the engine layer.** Every operation of a blocking call lives in a row of the same op table a `Submitter` uses, and every verdict (ticket, append reservation, poison, read classification) comes from one place for both.

## What changed in behaviour

- `Store::oldest_outstanding` reports a queue busy while an operation is in flight on it, from before the operation is submitted, and the age restarts when the queue's oldest operation completes.
- An append whose write the platform refused after its space was reserved poisons the store once, so `Store::poisoned` reports the OS code.
- A flush that panics poisons the store and releases flush leadership (before, every later barrier hung).
- On Windows a durable write no longer allocates (the flush's status block is reused).
- The observer's `Reads` and `ReadBytes` count reads that completed successfully and the bytes they returned.
- See the CHANGELOG for every change and fix.

## How it was verified

- **Crash replay on a real kernel:** dm-log-writes records every write, flush and FUA of a store workload on ext4 and XFS; the log is replayed to every prefix, and to subsets of the writes cached before each flush (all of them for runs of up to six writes, sampled beyond), and every receipt must hold.
- **Kernel matrix:** the suites on Linux 5.15, 6.1 and 6.6 in VMs; conformance on io_uring (thread-owned and shared rings), the synchronous tier and IOCP. The matrix is what found the registered-buffer hang above, before release.
- **60 s idle:** zero system calls, I/O and timer wakeups, on both Linux tiers.
- **Hot path:** no futex call and no timed wait in a submitter's steady-state loop (strace, CI); zero allocations after initialisation (counting allocator, in the gates and as tests on Linux and Windows).
- **Mutation testing:** every integrity guard on the list must be caught by the tests; none survives. Loom model-checks the buffer pool, the append frontier and the flush domain; Miri checks the unsafe buffer code and the io_uring ring indices (on a simulated kernel).
- **Performance gates** (`harness gates`, CI on a memory-backed device, relative to the raw primitive and fio, labelled Unverified per D-066): see the table below. CPU efficiency counts each side's whole process. Bare-metal and power-safe gates remain for 1.0 (dev/TODO.md).

## Upgrading

- `StoreOptions` gains `max_write` and `large_buffers` (a class of larger pool buffers for single large submitter operations: the defaults add 32 MiB to each store's pool, which Windows charges to the commit limit at creation), `linux_tier`, and `register_file` (on by default; Linux io_uring only; `register_file: false` turns it off). `StoreReport` is `#[non_exhaustive]` and gains `io` and `unavailable`. Code that builds `StoreOptions` with `..StoreOptions::default()` compiles unchanged.
- Linux stores use io_uring by default; `linux_tier: LinuxTier::Sync` uses no io_uring (one synchronous system call per operation, as in 0.3; calls with several buffers run on the submit pool's threads). Each io_uring queue (a store's parallel lanes, created on first use, and each submitter) holds two file descriptors: the ring and an eventfd.
- A lookup of a region the open could not use returns `Corruption` naming it (before: `NotFound`, as for a name that never existed), and `StoreReport::unavailable` lists such regions. `Store::open_readonly` takes a shared lock: readers share a store, and still exclude the writer.
- Outside implementers of `Platform` and `Queue` add `Platform::lock_shared` and `Platform::monotonic_ms`, `Queue::Waker` and `Queue::waker`; `QueueConfig` gains `parallel`, `pool_threads` and `owner`. `queue_registered`, `io_path` and `workers` have defaults.
- The on-disk format is unchanged: a 0.3.1 store opens with 0.4.0. One check is stricter: the volume record's reserved bytes, which every version so far wrote as zeros, must be zero.
