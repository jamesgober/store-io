# store-io v0.6.0: several devices, background pacing, read streams, export and import

**Stores on several devices made durable together, with dependent writes, and copies kept only on devices known to be distinct; background I/O paced against commits on each device; read streams and prefetch; and a store exported to a caller's sink, to a directory of files, or straight into a new store, then imported back with every byte checked. The container format is unchanged: a store made by 0.5 opens with 0.6. MSRV is unchanged: 1.85.** `0.x` releases make no compatibility promise, the on-disk format included; see Upgrading.

```toml
[dependencies]
store-io = "0.6.0"
```

## What is new

**Device and file identity** (`DeviceFacts::identity`). The probe names every physical device a store's bytes may live on, with the identifiers each reports: on Linux every whole disk under the file system (each leaf of a dm, md or LVM stack) with its namespace's `wwid` and its controller's serial and NQN; on Windows every disk of the volume with its serial and, for NVMe, its controller's; on macOS the device's IOKit path. `DeviceIdentity::distinct` errs one way only: two devices are known distinct only when both identities are complete and share nothing. A virtual machine's disks, RAID logical drives the probe recognises, cloud volumes, loop devices, pools and network storage are never complete, so never known distinct. Two gaps are documented: a RAID controller that presents its volumes as plain SATA or USB disks is not recognised, and a Windows guest running its own Hyper-V under another hypervisor reads as physical when its SMBIOS does too. Read without privilege and without a flush.
- A writable open now checks that the path still names the file it locked, so a container renamed over the path between the open and the lock cannot leave a writer acknowledging writes no later open can see.
- A writable open flushes its directory before its first write.

**`StoreSet`: several stores made durable together.**
- `barrier` and `barrier_each` flush each store at most once per call, in parallel, and keep each store's failure its own.
- `append_after` and `write_after`, on a region, a set or a `Submitter`, write bytes that point at durable bytes elsewhere: the write names the receipts it depends on, and they are checked before anything is reserved.
- `ditto` and `ditto_pages` write one copy per store, refused before any write (`NotWritten(SameDevice)`) unless every pair of devices is known to be distinct (with the gaps above).

**I/O classes and per-device pacing** (`IoClass`: `Commit`, `Read`, `Background`).
- Every store joins its device's group when it opens. Every commit barrier marks the device's commits active, which costs one clock read and a compare.
- While commits are active, background work has one piece in flight per call; while they are quiet, up to `background_unpaced` (8).
- Paced: a background `Submitter`, `copy_store` (its reads and its target alike), a caller's scans and export. A quiet `copy_store` still runs as fast as in 0.5.
- What is measured: G19, on CI's calibrated device (`null_blk` behind a delayed flush), one paced background `Submitter` on another store of the same device, auto-tuning off: a commit's p99 stays within twice idle, and with pacing off it must exceed twice (the negative control).
- `Store::commit_hold` keeps commits active while it lives, and `Store::qos` reports a device's pacing.
- Opt-in auto-tuning of the background budget (`background_autotune`) follows windows of commit latency; with it on, commits may run at up to 1.4x the latency of a window run at one piece in flight (documented, not gated).

**Read streams and prefetch.**
- `AppendRegion::read_stream` and `PageRegion::read_stream` return an iterator of owned `Chunk`s over any byte range, read on a queue of their own, so they hold nothing a commit needs.
- A range the device cannot read is an exact item, `Error::Corruption { kind: CorruptionKind::MediaError, .. }` with its range, and the stream goes on.
- A recycled or released region ends the stream, and no chunk ever holds bytes of a newer generation.
- `Store::prefetch` streams several ranges on one queue.

**Export and import.**
- `Store::export(sink)` pushes every region, in order, to an `ExportSink`: an `ExportHeader`, each region's `RegionInfo` and bytes, then `finish`.
- Three reference sinks and a source, each with a facade entry point:
  - `store_io::file_sink(dir, opts)`: a `FileSink` writes one data file per region and a `regions.info` record with a CRC-32C of every 1 MiB span (the export's record layout: `docs/FORMAT.md` Part III).
  - `store_io::file_source(dir, opts)`: a `FileSource` reads such a directory back, checking every span before its bytes are handed out.
  - `store_io::store_sink(to, opts)`: a `StoreSink` restores an export straight into a new store, with no files between.
- `store_io::import(source, to, opts)` builds a new store from any `ImportSource`, treating the source as untrusted.
- A failed import or restore renames nothing, and a crash leaves no store under the target name, or the whole one. A file export is complete only once its `regions.info` is written, at `finish`.
- What an export reports is only what its sink wrote: with a reference sink, a region counts once its bytes are durable, and nothing past a failed write is reported exported.
- `ExportHeader` and `RegionInfo` have byte forms (`to_bytes`, `from_bytes`) for a caller's own framing.

## What changed in behaviour

- **A writable open is refused (`Unsupported { DirectoryFlush }`) on a file system that cannot flush a directory**, as directory-mode changes already were. Read-only opens are unaffected.
- A writable open whose path, between its open and its lock, came to name another file retries once onto the file the path names now, then fails `Locked`. Any error reading the file's identity fails a writable open with `Io`; on Windows, so does an id of 0 or -1 (which some network servers report for every file). On Windows, a file system without 128-bit file ids (FAT, exFAT, some network servers) uses the 64-bit file index.
- An open now reads its device's identity, which adds about 0.3 ms on Linux and about 0.2 ms on Windows.
- Background I/O is paced while commits are active: a background `Submitter` returns `NotWritten(Paced)` for an operation whose first piece is refused (reap and retry); scans and copies run at one piece in flight beside active commits.
- On a power-safe store, durable metadata writes (a slot commit, provisioning, a clean close) mark commits active.
- Directory mode has a largest object, 16 MiB by default (from 0.5.1; see Upgrading).

## Published, not gated

Figures from CI run 44673210927 on commit 2ca70c4, the release's code (the release commit changes only comments, docs and one test's name) (memory-backed device for G20 and G21, G19's calibrated device for G19t), unless marked otherwise.
- **G21, an export to `FileSink` against fio reading and writing on the same device.** On CI's memory-backed device the export is about half of fio: 2,520 MB/s, 55% of fio's writer with its end fsync counted beside its reader (4,606 MB/s, a lower bound for fio), 47% of the lower of fio's read and write rates (5,391 MB/s), 58% of fio writing a fresh 1 GiB file alone (4,319 MB/s). Windows is slower still: measured during development on the dev box (NVMe, NTFS), the export ran at about 390 to 420 MB/s against fio's lower side of 2,308 to 2,366 MB/s (16 to 18%); fio writes a fresh file there at 1,960 to 2,181 MB/s, so the gap is in how the sink issues its writes, not NTFS alone. The next 0.6.x release works on the export's speed and gates G21 at 80%.
- **`StoreSink`'s export rate**, beside G21: 2,874 MB/s.
- **G20's `Background` read stream**, beside the gated `Read` stream: 7,495 MB/s (the `Read` stream 8,327 MB/s against fio's best sequential read of 8,964 MB/s, which G20 gates at 90%).
- **G19t, auto-tuning on**: a commit's loaded p99 at 1.44x idle, as the default's (1.44x), on G19's device.

## Fixed

- A caller's scan, and a `copy_store` into such a store, failed at their start with `NotWritten(PoolExhausted)` on a store whose `background_io` is not a power of two.
- A blocking write split into pieces, and a region's provisioning fill, now stop at a poison set by another operation (fail-stop), submitting nothing after it.

0.5.1's fixes are included. The full list is in `CHANGELOG.md`.

## How it was verified

Nothing is certified power-safe yet: power-cut certification is 0.9's work.
- The full test suites on Linux, Windows and macOS, on stable and 1.85; clippy, rustdoc, Miri on the buffers, loom (now also over pacing's admission and auto-tuning, the set barrier and read streams); the conformance suite on APFS (CI), NTFS, ext4 and XFS; the kernel matrix (5.15, 6.1, 6.6 in VMs); the dm-log-writes crash replay; the fail-stop job; fuzz smoke (the export record has its own target); `cargo audit`, `deny` and `vet`.
- **A multi-device CI job:** four `null_blk` devices with one store each (CI run 44673210927).
  - G17, summed sequential writes over 1, 2 and 4 devices, at least 90% of fio on the same devices together: 98.6%, 98.7% and 107.2% of fio (98 to 110% across 0.6's runs, per the CHANGELOG).
  - G18, a set barrier within 2 µs + 3% of the raw parallel barrier: passes (set p50 47.3 µs, raw 46.8 µs). The job accepts a PASS or a NOT RESOLVABLE for each.
- **G19 on a calibrated device** (CI run 44673210927): a commit's p99 beside one paced background `Submitter` at 1.44x idle (at most 2x), and 3.14x with pacing off (must exceed 2x). Its variants pass: a `CommitHold` keeping sparse commits active, checkpoints with barriers, and 3 minutes under load.
- **Every crash point:** the simulator cuts the power at every step of an import, a `FileSink` export and a `StoreSink` restore: each leaves no store (or no complete backup), or the whole one.
- **Mutation testing:** every integrity guard has a mutation entry, or a recorded reason it has none: 1,490 entries, and the mutation run on the release's code (run 44673211073) passes with no survivor.
- **Idle:** an idle store with 0.6's machinery (a set, a registered background `Submitter`, a hold dropped halfway) makes no system call, wakeup, timer or I/O for 60 s on every system.
- **Performance gates on CI's memory-backed device with io_uring** (CI run 44673210927): every gated row passes.
  - G1, a lone 4 KiB durable write: a median 0.90 µs over `pwritev2` + `fdatasync` (interval 0.81 to 0.94; raw p50 13.7 µs) against a 2 µs gate, 0 of 20 rounds over. 0.5.0 measured 0.46 µs. Each commit barrier now reads the clock once (`CLOCK_MONOTONIC`, 29 ns a read on this runner, a hot-loop figure and so a lower bound on a commit's: about 30 ns of the 0.44 µs rise) and, at most once a millisecond, stores it to mark the device's commits active; the gap also follows the runner: an earlier 0.6 CI run measured 0.47 µs over a 6.0 µs raw write.
  - G20, a `Read` read stream: 8,327 MB/s against fio's best per round of 8,964 MB/s, about 93% (at least 90%).

## Upgrading

- Replace `0.5` with `0.6`. Most code compiles unchanged; these changes can need edits (each in `CHANGELOG.md`):
  - **For implementers of `Platform`**, seven required methods: `device_identity`, `file_identity`, `path_identity`, `monotonic_ns`, `clock`, `free_space` and `dir_is_empty` (`identity_scope` has a default).
  - **Fields added to public structs:** `StoreOptions` (`background_io`, `background_unpaced`, `background_pacing`, `commit_quiet`, `background_autotune`, `background_depth_max`), `DeviceFacts` (`identity`, `members`) and `FsFacts` (`device`). Build them with `..Default::default()`.
  - **`observe::Counter`** gains `Dependencies` (`COUNTERS` is 10): an exhaustive `match` on it needs the new arm.
  - **`NotWrittenCause`** gains `Paced`, `NotPrefix` and `SameDevice` (it is `#[non_exhaustive]`).
  - **In the simulator**, `TraceEvent::Read` gains `len`, and a flush now makes durable only its own file's cached writes. A test that relied on one file's flush covering another's fails; `SimConfig::share_flushes` restores the old behaviour, every file's on the same device.
- **From 0.5.0: directory mode has a largest object, 16 MiB by default** (0.5.1). An object over 16 MiB written by 0.5.0 is unreadable at the default; open the handle with `Directory::with_max_object` to read it.
- **The container format is unchanged:** a store made by 0.5 opens with 0.6 as it is.

## Next

The 0.6.x releases add, in order:
1. The export's speed: its reads and writes overlapping, zero-copy writes, `StoreSink` and Windows; G21 gated at 80%.
2. Range clone and unshare: a range shared with another file without copying its bytes, where the file system can (XFS with reflink; btrfs and ReFS too, where a store stays Unverified), and made private again before it is written.
3. Copy-and-swap: a copied store put in place of the original under its path.
4. Write-combining append regions: small appends from many callers packed into the region's tail and written together.
5. Shadow paging: regions updated by transactions of whole pages, with snapshots.
6. Many-file mode: a batch of directory-mode replaces made durable with one directory flush.
7. NUMA and the registration hook: a store's buffers and flush thread placed on its device's node, and a hook for registering its buffers with another I/O layer.
8. Flush-sharing conformance per file system, then the 0.6 exit gate.

Then 0.7, the alpha (documentation, polish, tuning and testing); 0.8, raw NVMe namespaces and passthrough; 0.9, power-cut certification and the bare-metal measurements; and 1.0, the stable API and format. See `dev/ROADMAP.md`.
