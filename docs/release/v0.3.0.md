# store-io v0.3.0 &mdash; Usable

**The first release a database can build on.** Stores, regions, batches,
small-object slots, raw recovery scans, recycle and release, space
reservations and atomic file replace, through a simple API with no generics
in your code, on Windows and Linux. Every durable write produces an
unforgeable receipt at a durability class decided from what the device
itself reports, and the first failed write or flush stops everything.

## What is store-io?

The storage I/O layer for Rust databases and storage engines, and the
replacement for [fsys](https://github.com/jamesgober/fsys-rs). It moves caller
bytes between memory and media and proves when they are durable:

- **Durability classes from evidence.** Each store is classed as power-safe,
  flush-required, unverified or unsafe from the device's own evidence;
  unsafe and unverified devices are refused unless you attest or override,
  and every receipt says which.
- **Unforgeable receipts.** Positions, write tickets and receipts are typed
  values only store-io can create; `receipt.covers(&ticket)` is exact.
- **Fail-stop.** The first failed or short write or failed flush poisons the
  device's barrier domain; a flush is never retried.
- **Nothing hidden.** No framing, no repair on open, no timers, no
  group-commit windows, no idle wakeups.

## What's in 0.3.0

```rust
use store_io::{Store, StoreOptions};

let store = Store::create("data/orders", StoreOptions::default())?;
let wal = store.provision_append_region("wal", 256 << 20)?;
let (pos, receipt) = wal.append_durable(b"order 1001")?;   // one write, one flush

let mut batch = wal.batch();                                // many records,
batch.append(b"order 1002")?;                               // one write,
batch.append(b"order 1003")?;                               // one flush
let (start, receipt) = batch.commit()?;
```

- **Regions.** Append regions (store-io chooses positions, blocks are never
  rewritten) and page regions (your positions, overwritten in place); writes
  and reads of any size.
- **Batches.** `AppendBatch` packs records into the device's own buffers
  (encode in place with no copy); `PageBatch` submits many pages before one
  barrier.
- **Many writers.** Concurrent barriers share device flushes by the join
  rule: no timer, no window, and a lone writer never waits for company.
- **Small objects.** `Slot` (old or new after any crash) and `Directory`
  (`replace` swaps a whole file atomically and durably).
- **Recovery.** Read-only opens that change nothing; `scan` reads a region
  in order with eight reads in flight and never stops at bad data
  (unreadable ranges are narrowed to blocks and reported); `resume_at`.
- **Lifecycle and space.** `recycle` (new generation, header only),
  `release` (table first, then header, then the space), `reserve` with
  per-tag caps and accounting.
- **The device report and the `store-io probe` tool** (feature `cli`).
- **Crates:** `store-io` (the simple API), `store-io-engine`,
  `store-io-core`, `store-io-format`, `store-io-buf`, `store-io-platform`,
  `store-io-win`, `store-io-posix`, `store-io-sim` (the deterministic
  simulator) and `store-io-conformance` (the suite every backend must pass).

## Performance

Measured on the development machine (consumer NVMe, NTFS, flush-required by
evidence), against the raw write-and-flush primitive and fsys 1.1.3 on the
same box. The full reports, with the device report and every option, are in
[`harness/results`](https://github.com/jamesgober/store-io/tree/main/harness/results).

| Workload | vs raw | vs fsys |
|---|---|---|
| Lone durable 4 KiB append | 1.03&ndash;1.06x (steady state) | 1.29&ndash;1.31x (43x fsys's default configuration) |
| 64 concurrent durable writers | 23x | 1.76x |
| `AppendBatch`, 1000 &times; 64 B | 2.6x | 3x |
| `PageBatch`, 64 pages | 0.73&ndash;1.48x | 11&ndash;22x |
| Sequential 1 MiB writes | 0.91&ndash;1.06x | 2.9&ndash;3.5x |
| Sequential 8 MiB reads | 1.04x | (no comparable fsys read) |

A lone durable write already runs at the device floor (the flush is about
290 &micro;s on this drive). A consumer drive is noisy: right after gigabytes
of writes, any workload can run several times slower for a while, so every
figure here was repeated. Known gaps, recorded in the later list: many
unbatched small appends followed by one barrier (use `AppendBatch`, which is
1.4&ndash;4x fsys), and the Linux synchronous tier running batches and large
reads one operation at a time until io_uring in 0.4.

## Verification

- A deterministic simulator with a volatile device cache, crash enumeration
  over every subset of cached writes, and fault injection (failed, short,
  lost and misdirected writes; failed and lying flushes; unreadable ranges;
  out of space).
- loom models of the lock-free code and Miri on the unsafe buffer code, both
  in CI; a compile-fail suite for the typed positions, tickets and receipts;
  every planted bug in a 38-case mutation list is caught.
- The conformance suite on NTFS, ext4 and XFS, and a device-mapper run that
  fails every I/O mid-write on a real Linux kernel: no write succeeds after
  the first failure, and every acknowledged record survives.

Run on Windows x86_64 and Linux (WSL2), Rust stable and 1.85:

cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace --all-features
RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps --all-features

## Breaking changes

None from 0.1.0, which had no API. `0.x` releases make no compatibility
promise, and the on-disk format may still change before 1.0.

## What's next

0.4 brings io_uring on Linux and the engine layer (a per-thread submitter
with owned buffers and completion tags); 0.5 brings macOS. Power-cut
certification of the durability claims comes with 1.0.
