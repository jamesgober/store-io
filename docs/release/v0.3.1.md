# store-io v0.3.1 &mdash; Safety fixes

**A patch release for five defects in 0.3.0. Two could lose acknowledged data
and one could hang a store. Every 0.3.0 user should upgrade.** The on-disk
format and the public API are unchanged: a 0.3.0 store opens with 0.3.1, and
code that compiled against 0.3.0 compiles against 0.3.1.

```toml
[dependencies]
store-io = "0.3.1"
```

## What was wrong

**1. `Store::create` could empty a real store.**
- When `store.sio` already existed, `create` treated it as the leftover of a create that crashed, and emptied it, when all three held:
  - it was unlocked;
  - it was at most 256 KiB;
  - its volume record could not be found.
- The record could also be missing from a real store:
  - after a transient read error;
  - with both copies of the record damaged;
  - for a store written by a newer version;
  - when the buffer pool was momentarily empty.
- A small store (slots and small regions) fits in 256 KiB. Code that calls `create` after a failed `open` could lose everything in it.

**2. Release and recycle could lose acknowledged writes.**
- After writing a metadata record durably, store-io read it back from the device. If that read failed, the operation was reported as not written and the region was reopened, although the release or recycle was already durable.
- Writes acknowledged after that point were lost on the next open, and a later provisioning could reuse the space.
- The same read-back could make a small-object slot return its previous version right after a commit had returned a receipt for the new one.

**3. Concurrent small-object commits and flushes could deadlock.**
- A slot commit (or a header rewrite, table update or provisioning step) kept its I/O queue while waiting for a flush led by another thread.
- That thread needed a queue to run the flush. With every queue held this way, the store hung until `Store::poison()`.

**4. A failed provisioning write did not stop the store.**
- A fill write that failed or came back short after submission was reported, but the store kept accepting writes.
- store-io is fail-stop: the first failed write poisons the store.

**5. `resume_at` on a read-only store could overstate durability.**
- `AppendRegion::resume_at` advanced `durable_through()`. On a writable open that is backed by the device flush the open performs; a read-only open performs none.

## What 0.3.1 does

- **`create` takes over only a file that provably never held a store.**
  - Every block is read in full, and no block may hold a slot header whose header CRC verifies.
  - Anything else, including an unreadable file, a damaged store or one from a newer version, is left untouched with `AlreadyExists`.
  - A create that crashed before its metadata was durable is still taken over.
- **Nothing is read back after a durable metadata write.** The new state comes from the exact bytes written, validated in memory with the same checks a read applies. That also saves one device read per metadata commit.
- **The thread leading a flush uses a queue of its own.** It never waits for one, so no wait cycle can form. Each store opens one more platform queue than `StoreOptions::queues`.
- **A fill write that fails or comes back short after submission now poisons the store**, with `DurabilityUnknown`. Running out of space is still `NoSpace` and poisons nothing.
- **`resume_at` is refused on read-only stores**, with `NotWritten(ReadOnly)`.

## How it was found and verified

- The defects were found while writing up the design changes made during 0.3.0 and re-mapping every source file against the design.
- Each one is reproduced by a test on the deterministic simulator that fails on 0.3.0 and passes on 0.3.1 (`crates/store-io-engine/tests/hazards.rs`). One more test checks that a create torn in the middle of its first header is still taken over.
- The full workspace test suite, clippy, rustdoc, the conformance suite on NTFS, ext4 and XFS, loom, Miri and the dm-error fail-stop job all pass. CI is green on the release commit.

## Upgrading

- Replace `0.3.0` with `0.3.1`. No code changes are needed.
- If your code calls `Store::create` after `Store::open` fails, check why `open` failed first. 0.3.1 no longer destroys a store in that case, but `create` returns `AlreadyExists` for a store that exists and cannot be opened. That store needs recovery (`Store::open_readonly`, `scan`), not re-creation.
